# 需求澄清提问维度清单

本文件列出需求澄清阶段可覆盖的提问维度。AI 应根据项目类型和已有信息**选择性提问**，一次只问一个问题，不逐条轰炸。用户回答后判断是否需要继续追问，或切换到下一个维度。

## 核心维度（优先覆盖）

### 1. 项目背景与目标
- 这个项目是为了解决什么具体问题？
- 谁会使用这个项目？使用场景是什么？
- 项目成功的标准是什么？（比如：节省多少时间、达到什么效果）
- 有没有类似的现有工具或方案？它们哪里不够好？

### 2. 功能范围
- 核心功能有哪些？按优先级排一下。
- 哪些功能是第一版必须有的，哪些可以以后再加？
- 有明确不做的功能吗？（划清边界，避免范围蔓延）

### 3. 技术栈与平台
- 项目用什么编程语言/框架？（如果用户不确定，可根据需求推荐）
- 运行在什么平台上？（Windows / macOS / Linux / 浏览器 / 移动端 / 服务器）
- 需要和其他系统或 API 对接吗？
- 有没有已有的代码库或项目结构需要兼容？

### 4. 输入与输出
- 项目的输入是什么？（文件路径、命令行参数、用户输入、API 请求等）
- 项目的输出是什么？（生成文件、打印结果、界面展示、API 响应等）
- 有没有具体的输入输出格式要求？（JSON、CSV、特定文本格式等）

### 5. 依赖与环境
- 运行这个项目需要安装什么依赖？
- 有没有特定的版本要求？
- 需要配置环境变量或配置文件吗？

## 扩展维度（按需覆盖）

### 6. 性能与规模
- 预计处理的数据量有多大？
- 对响应时间或吞吐量有要求吗？
- 需要支持并发或多用户吗？

### 7. 错误处理与边界
- 输入异常时应该怎么处理？（报错提示、跳过、默认值）
- 有没有需要特别处理的边界情况？

### 8. 安全与权限
- 涉及敏感数据吗？需要加密或脱敏吗？
- 需要用户认证或权限控制吗？

### 9. 交付形式
- 最终交付什么？（单个脚本、可执行文件、完整项目目录、Docker 镜像等）
- 需要打包成可分发的形式吗？

## 提问原则

1. **一次一个问题**：不要一次抛出多个问题，避免用户压力。
2. **先核心后扩展**：优先覆盖核心维度，扩展维度按需补充。
3. **根据回答自适应**：用户回答充分的维度不再追问；回答模糊的维度继续深挖。
4. **不替用户做决定**：技术选型等关键决策先问用户偏好，用户不确定时再给建议。
5. **可随时结束**：用户说"够了""开始做""不用问了"等，立即停止提问，进入需求汇总确认环节。
