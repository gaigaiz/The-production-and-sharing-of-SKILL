# Project Builder — 通用项目从零构建

## 工作流总览

本 skill 定义三阶段串行工作流，必须严格按顺序执行：

```
阶段一：需求澄清 → 阶段二：项目制作 → 阶段三：文档生成
```

每个阶段完成后需获得用户确认（或用户明确指令）才能进入下一阶段。

---

## 阶段一：需求澄清

### 启动条件

用户提出项目想法或功能需求，但以下信息中至少有一项不明确时，进入本阶段：
- 项目要解决的具体问题
- 技术栈 / 编程语言
- 运行平台
- 输入输出形式

### 提问规则

1. **一次只问一个问题**，不得一次抛出多个问题。
2. 从核心维度开始，按优先级逐步深入。提问维度参考 [references/clarification-questions.md](references/clarification-questions.md)，根据项目类型选择性覆盖，不逐条照搬。
3. 用户回答后，判断信息是否充分：充分则进入下一维度或停止追问；不充分则继续深挖该维度。
4. 技术选型等关键决策先询问用户偏好；用户表示不确定时，给出 1-2 个推荐方案并说明理由，由用户选择。
5. 不替用户编造需求、预算、平台或验收标准。

### 用户手动结束机制

用户在任何时候说出以下任一表述，立即停止提问，不得继续追问：
- "够了"、"不用问了"、"问完了"、"可以了"
- "开始做吧"、"开始制作"、"动手吧"、"直接做"
- "进入下一步"、"下一个阶段"
- 或其他明确表示结束提问、开始制作的指令

### 需求汇总确认

停止提问后，先输出一份**需求摘要**，包含：
- 项目目标与背景
- 核心功能列表
- 技术栈与运行平台
- 输入输出形式
- 已明确的约束条件

然后询问用户："以上需求是否准确？确认后开始制作。" 用户确认后进入阶段二；用户提出修改则调整后再次确认。

---

## 阶段二：项目制作

### 执行规范

1. 根据阶段一确认的需求，在用户指定的目录（或当前工作目录）下创建项目文件。
2. 先规划项目结构（目录、文件清单），告知用户后再开始编写代码。
3. 代码编写遵循对应语言的通用规范，添加必要的注释。
4. 制作过程中如遇到需求未覆盖的决策点，暂停并询问用户，不擅自做重大决定。
5. 关键功能完成后，如可运行则进行简单自测，确保基本功能正常。

### 与用户沟通

- 制作开始时告知预计的文件结构和实现思路。
- 制作过程中定期同步进度（每完成一个主要模块）。
- 制作完成后，列出已创建的文件清单和实现的功能点，供用户确认。

---

## 阶段三：文档生成

### 文档要求

项目制作完成并经用户确认后，生成项目说明文档。文档命名为 `README.md`（如项目已有 README 则命名为 `项目说明.md`），放在项目根目录。

文档必须严格按照固定五段式结构编写，详细模板和示例见 [references/doc-template.md](references/doc-template.md)：

1. **项目解决什么问题** — 项目背景与目标
2. **主要功能** — 核心功能点列表
3. **安装方法** — 依赖安装与环境配置步骤
4. **使用方法** — 基本运行 / 调用方式
5. **输入输出示例** — 至少一个可运行的完整示例，包含输入和预期输出

### 生成后验证

文档生成后，按以下清单逐项自检（在内部完成，不向用户展示清单）：
- 五个章节全部存在，无遗漏
- 安装命令可直接复制运行
- 使用示例包含真实可运行的命令
- 输入输出示例完整，输入和预期输出都明确
- 无 TODO、xxx 等占位符；信息确实不足时标注"待补充"并说明原因

自检通过后，告知用户文档已生成，并简要说明文档位置和内容结构。

---

## 状态管理与中断恢复

- 当前处于哪个阶段，在每次回复开头用一句话标注，例如：`[需求澄清阶段]`、`[项目制作阶段]`、`[文档生成阶段]`。
- 如果会话中断后恢复，根据上下文判断当前阶段，主动告知用户并询问是否继续。
- 用户在任何阶段都可以说"回到需求澄清"、"重新确认需求"来回到阶段一。
