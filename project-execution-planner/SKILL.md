# Project Execution Planner

将口语化项目需求转化为结构完整、可执行的项目执行计划 Markdown 文档。

## 工作流程

### 第 1 步：输入校验与规范化

检查用户输入是否为分步格式（`第 1 步：xxx；第 2 步：xxx；第 3 步：xxx`）。

- **是分步格式** → 直接进入第 2 步。
- **非分步格式（自由文本）** → 向用户提示：
  > 检测到您的输入为自由文本。建议按「第 1 步：xxx；第 2 步：xxx」格式重新输入，或我可以自动将当前文本拆分为分步需求条目。是否自动拆分？
  
  等待用户确认后再继续。用户明确同意自动拆分时，按语义边界将自由文本拆分为编号步骤，并在文档「原始需求原文」中保留原始文本。

### 第 2 步：需求理解与冲突检测

逐条阅读需求，提取以下信息：
- **业务功能**：需要实现/修改的功能点
- **工程环境**：技术栈、框架、运行环境、依赖版本
- **代码基线**：现有代码结构、涉及模块、已有实现

**冲突检测**：若多条需求之间存在矛盾（如同时要求"保留旧接口"和"删除旧接口"），在文档中标明冲突项，向用户确认取舍，**不擅自取舍**。

### 第 3 步：方案选定与备选记录

若某需求存在多个可选实现方案：
- 默认选定其中一个方案写入执行计划（选择标准：对现有代码侵入最小、实现成本最低、与项目技术栈最匹配）。
- 在文档「工程前置约束」或对应任务备注中列出其余备选方案及简要说明。
- 用户后续指定更换方案时，重新评估代码影响并更新计划。

### 第 4 步：任务拆解与依赖分析

将每个需求步骤拆解为可执行子任务，每个子任务包含：
- **子任务名称**：简洁描述要做什么
- **优先级**：P0（阻塞性，必须先完成）/ P1（核心功能）/ P2（增强项）
- **依赖**：前置子任务编号，无依赖则标注「无」
- **预估涉及文件/模块**：列出可能需要修改的代码文件或模块

按依赖关系排序，确保无循环依赖。

### 第 5 步：代码变更影响评估

对每个涉及代码修改的子任务，评估：
- **修改范围**：新增 / 修改 / 删除
- **影响面**：该变更可能影响的其他模块或功能
- **兼容性**：是否破坏现有接口、数据结构或调用方

**代码修改原则（硬性约束）**：
1. 所有代码变更必须保证不破坏原有项目代码功能。
2. 当用户明确要求移除某项功能时，必须先检查待删除功能的代码依赖（被哪些模块调用、是否有共享逻辑），确认删除操作不会影响其余代码功能，并在计划中写明校验方式（如：运行现有测试套件、检查调用方编译、执行回归用例）。

### 第 6 步：风险与校验项识别

识别执行过程中的风险点，并为每个风险指定校验方式：
- **技术风险**：如第三方依赖兼容性、性能瓶颈
- **集成风险**：如模块间接口不一致、数据迁移
- **回归风险**：如修改可能影响已有功能

每个校验项应明确：校验内容、校验时机（开发中 / 提测前 / 上线前）、校验方法（自动化测试 / 手动验证 / 代码审查）。

### 第 7 步：生成 Markdown 执行计划

按照 `references/plan-template.md` 中的固定章节模板生成文档。读取该模板获取完整结构和填写指引。

固定章节（不可遗漏）：
1. 项目概述
2. 原始需求原文
3. 工程前置约束
4. 任务拆解（子任务 / 优先级 / 依赖）
5. 代码变更规则
6. 风险与校验项
7. 交付物清单
8. 回滚方案

### 第 8 步：迭代更新（增量模式）

用户后续修改需求时：
1. 读取原有执行计划文档。
2. 识别变更点（新增 / 修改 / 删除需求）。
3. 重新评估受影响的子任务、依赖关系和代码影响。
4. 在文档末尾追加「版本变更记录」，记录：版本号、变更日期、变更内容、影响范围。
5. 输出更新后的完整文档。

## 范围边界

- 本执行计划用于**任务拆解**和**代码变更影响评估**。
- 默认**不直接生成完整项目代码**。
- 可根据用户额外指令补充关键代码片段（如接口定义、核心逻辑伪代码），但不替代完整实现。
